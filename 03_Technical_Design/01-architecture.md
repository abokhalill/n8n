# Phase 1 — Architecture Design Note

Lead processing pipeline. n8n orchestration, Postgres state, all external systems mocked.

Every mechanism below is introduced by the numbered edge case (brief §4) that forces it. Where a mechanism exists for a reason other than a listed edge case, that is stated.

---

## 1. Scope and deliberate cuts

**Built in full:** multi-source intake (website, WhatsApp, CSV), canonical normalisation, validation with a data-completion path, duplicate detection with confidence tiers, mocked enrichment, deterministic scoring, AI classification with conflict routing, routing and workload assignment, VIP approval gate, follow-up engine, booking/conversion handling, mocked Odoo sync with stage transitions, retry/dead-letter/reprocessing, audit trail. All 14 edge cases with reproducible evidence.

**Deliberately cut, with the approach I would take:**

| Cut | Why | How I would finish it |
|---|---|---|
| Operational summary as a SQL view + screenshot, not a dashboard | Brief §3.J asks for "a simple operational summary". A view answers every question asked; a dashboard is presentation work, not engineering signal | Grafana against the same view, or an n8n cron posting the summary to Slack |
| Email as a `channel` field on the existing dispatcher, not a second integration | The dispatcher's idempotency, claim/commit and hold logic are channel-agnostic. | Thin CSV path — parse, per-row validate, per-row isolate | Edge case 13 (corrupted row in a valid batch) is the only requirement here, and it is about *row isolation*, not throughput | Chunked streaming with a per-file manifest and resumable offset for large files |
| No real Odoo | Brief §8 permits mocking. See §11 for where the mock diverges from real Odoo semantics | XML-RPC/JSON-RPC client with `x_idempotency_key` as an indexed field; see §11 |

## 2. Assumptions

1. **Volume is low** — hundreds of leads/day, not millions. This justifies a 1-minute scheduler tick and Postgres-as-queue rather than Kafka/Redis Streams. At 10⁵+/day the tick model would need replacing; that threshold is stated so the design's expiry date is explicit.
2. **A lead's identity is a person, not a submission.** Two submissions from the same human are one lead with two source events. This is the premise dedup is built on.
3. **Consent is per-channel and revocable at any time**, including while work is scheduled. Opt-out is checked at dispatch, never cached.
4. **Sales reps and their capacity live in our store**, not Odoo. Real deployments usually read this from the CRM; here `sales_rep` is seeded locally so workload assignment and edge case 9 are demonstrable without a live Odoo.
5. **"Sales action" for the 30-minute SLA (brief §5) means an explicitly logged rep action** — a recorded contact attempt or a stage advance by a human. Viewing a record does not count. The brief does not define this; a narrow definition is the safe one because a broad one makes the SLA unenforceable.
6. **"Materially conflict" (brief §3.D) means the AI label and the deterministic band are more than one band apart, with AI confidence ≥ 0.6.** Adjacent-band disagreement is noise; a confident two-band gap is a real disagreement. Edge case 5 is exactly this predicate.
7. **The booking provider supplies a stable booking ID.** Edge case 11's dedup key is the provider's ID, not our receipt of it.
8. **One n8n instance, queue mode capable.** The design assumes multiple workers may run concurrently and never assumes single-threaded execution.
9. **Clock skew between n8n and Postgres is negligible.** All scheduling timestamps are generated by Postgres (`now()`), not by n8n, to make this true by construction rather than by hope.
10. **Mocked providers are cooperative on reconciliation** — they support lookup-by-idempotency-key. §11 records where real providers do not.

## 4. Idempotency — the single mechanism

### 4.1 Key structure

```
v1:{effect_domain}:{entity_type}:{entity_id}:{occurrence}
```

Derived **purely** from stable inputs. Never contains `$execution.id`, a timestamp, a random value, or an attempt counter (D-002).

| Effect | Key | Occurrence is… |
|---|---|---|
| Create the Odoo lead | `v1:odoo.lead.create:lead:01J8X…:1` | constant — a lead is created once |
| Welcome message | `v1:msg.send:lead:01J8X…:welcome` | the template slot, so a retry collides but a later message does not |
| Follow-up step 2 | `v1:msg.send:lead:01J8X…:followup.2` | the step index |
| Set stage | `v1:odoo.stage.set:lead:01J8X…:meeting_booked` | the target stage — naturally idempotent |
| Apply a booking | `v1:booking.apply:booking:BK-991:1` | the *provider's* booking ID. **Edge case 11** |

### 4.2 Three uses, one key

**(a) Inbound suppression** — `INSERT … ON CONFLICT DO NOTHING RETURNING key`. Zero rows returned means already handled: return the stored prior response, do not re-execute. Covers edge cases 11 and webhook redelivery generally.

**(b) Outbound claim/commit** — the interesting one, and the one a seen-set gets wrong.

```
1. INSERT claim (key, state='in_flight', attempt=n)  ON CONFLICT DO NOTHING RETURNING *
2.   if no row returned → read existing claim:
        succeeded  → skip the call, reuse stored response
        failed_permanent → skip, do not retry
        in_flight & fresh → another worker owns it; requeue with backoff
        in_flight & stale → RECONCILE (below)
3.   if row returned → we own the claim → make the external call
4. UPDATE claim SET state='succeeded'|'failed', response=…, provider_ref=…
```

**Reconciliation** is what resolves edge case 7. A stale `in_flight` claim is genuinely ambiguous — the call may have landed and the ack may have been lost. Guessing is not acceptable in either direction, so we *ask*: query the provider for an object carrying this idempotency key. Found → settle to `succeeded` and adopt the provider's reference. Not found → settle to `failed` and allow a retry. This is why the mocks must support lookup-by-key (D-016), and it is the single load-bearing requirement the mock harness places on Phase 2.

**(c) Replay (edge case 14)** — is not a feature. Because keys derive from stable inputs, a re-run recomputes *identical* keys, so every already-committed effect short-circuits at step 2. Replay safety is a consequence of §4.1, and that is the claim to make in a walkthrough.

### 4.3 The link that makes replay work

Derived-key idempotency only holds if `lead_id` is itself stable under redelivery. If a redelivered webhook minted a fresh ULID, every downstream key would differ and the whole chain would double-fire.

So: intake is keyed on `source_event_key = hash(source, provider_event_id ?? canonical_payload)`. The unique index on that column maps event → `lead_id`. A redelivery finds the existing mapping and reuses the original `lead_id`. This is the one place where getting it wrong silently defeats everything downstream.

**Edge case 1 is deliberately *not* this.** WhatsApp and website submissions from the same person are two genuinely distinct events → two `source_event_key`s → two `lead_id`s → resolved by the dedup stage (§5), which *links* them. Idempotency suppresses the same event twice; dedup resolves two events about one person. Conflating the two layers is the classic failure here (D-004).

## 5. Duplicate detection

Independently-derived features, published weights, full vector logged:

| Feature | Weight | Rationale |
|---|---|---|
| `phone_e164` exact | decisive | Post-normalisation, so **edge case 2** is handled before comparison |
| `email_normalized` exact | decisive | |
| Email local-part exact, different domain | 0.35 | Same human, work vs personal address |
| Name similarity (Jaro-Winkler on normalised) | 0.25 × sim | |
| Company match | 0.15 | |
| Submitted < 24h apart | 0.10 | |
| **Different source** | 0.10 | Cross-source is **edge case 1's signature**, so distinct sources *raise* suspicion rather than lower it |

**Tiers:** ≥ 0.90 auto-merge · 0.65–0.90 manual review · < 0.65 distinct.

**Contradiction demotion:** a decisive identifier match is demoted into the review band when other evidence contradicts it — same phone, different email *and* low name similarity. Shared office lines and family numbers are real; a rule that merges on phone alone will eventually merge two different people.

**Threshold defence.** The numbers are priors, not fitted values, and I will say that plainly. What is defensible is the shape: a false merge is destructive and customer-visible; a false split is cheap and self-healing when a human merges later. So the boundary sits conservatively, the ambiguous band goes to a person, merges are non-destructive (D-010) so even a wrong auto-merge is reversible, and every decision logs its full feature vector so the thresholds can be *fitted from outcomes* instead of argued about. The strongest claim is not "0.90 is correct" — it is "the system is instrumented to discover what is correct."

**Pipeline behaviour for probable duplicates:** processing continues (enrichment, scoring — all reversible), while CRM create and outbound messages are held pending review. Governing principle: **gate the irreversible, not the reversible.**

## 6. Scoring, AI, and conflict

Deterministic score is authoritative for routing. The AI emits an independent label + confidence from `free_text_need` only. The AI never touches the score (D-012).

- **Edge case 4** — the LLM is treated as an untrusted service returning untrusted bytes. Response is JSON-schema validated; on empty/malformed/timeout the classification degrades to `fallback_used: true` with a null label. The pipeline never blocks on the AI.
- **Edge case 5** — `conflict_flag` is set when the AI label and the score band are more than one band apart *and* AI confidence ≥ 0.6, which routes to `manual_review` regardless of score. The predicate is versioned alongside the score model.

## 7. The scheduler — one mechanism for three requirements

Bounded-backoff retry, follow-up steps, and SLA escalation are all "do X at time T, revalidating state at T." One `work_queue` table, one 1-minute cron dispatcher.

```
lease:  UPDATE work_queue SET state='leased', lease_until=now()+'5 min', lease_token=$1
        WHERE id IN (SELECT id FROM work_queue
                     WHERE state='pending' AND run_after <= now()
                     ORDER BY run_after LIMIT $2
                     FOR UPDATE SKIP LOCKED)
        RETURNING *
```

`SKIP LOCKED` makes concurrent dispatch safe under n8n queue mode. Lease expiry gives crash recovery — which makes the queue **at-least-once by design**. That is intentional: correctness comes from the idempotency layer beneath it, not from the transport.

**Revalidation at dispatch** is the whole point:
- **Edge case 10** — opt-out while a follow-up is scheduled: the dispatcher re-reads consent before sending and drops the item. The scheduled row is never trusted to still be valid.
- **Edge case 9** — rep unavailable between assignment and follow-up: ownership is re-resolved at dispatch, triggering fallback reassignment.
- **Edge case 3** — enrichment times out twice then succeeds: attempts 1 and 2 requeue with backoff; attempt 3 lands. Handled by the same rows.

**Backoff:** `random(0, min(2s × 2^attempt, 15min))`, 5 attempts. Full jitter to decorrelate retry storms. Retryable = 429/408/5xx/timeout (429 honours `Retry-After`). Terminal = other 4xx, missing credentials → straight to dead-letter, no wasted attempts (D-007). **Edge case 6** is the 429 path.

**Dead-letter and reprocessing.** Exhausted or terminal items land in `dead_letter` with the full payload and the originating idempotency key. Manual replay re-enters through the normal path with *the same keys*, so previously-committed effects short-circuit — safe reprocessing is again a consequence of §4.1, not a separate mechanism. **Edge case 14.**

## 8. Workflow decomposition

Split at three boundaries: **trust** (different auth and payload ownership), **retry** (n8n retries a whole execution, never a suffix — so anything independently retryable must be independently executable), and **time** (anything happening later cannot share an execution with anything happening now).

| Workflow | Trigger | Responsibility |
|---|---|---|
| `wf-01-intake-website` | Webhook | Normalise → persist source event → enqueue → ack fast |
| `wf-02-intake-whatsapp` | Webhook | as above |
| `wf-03-intake-csv` | Manual/Form | Per-row isolation. **Edge case 13** |
| `wf-10-pipeline-core` | Queue consumer | Validate → dedup → enrich → score → classify → route. Per-stage checkpointed |
| `wf-20-outbound-dispatch` | Queue consumer | **Only** workflow permitted to send messages. **Edge case 8** |
| `wf-21-odoo-sync` | Queue consumer | **Only** workflow permitted to write Odoo. Stage lattice guard |
| `wf-30-scheduler-tick` | Cron 1m | The timer wheel: due retries, follow-ups, SLA checks, approval expiry |
| `wf-40-booking-webhook` | Webhook | Inbound dedup on provider booking ID. **Edge case 11** |
| `wf-41-approval-callback` | Webhook | VIP approve/reject. **Edge case 12** |
| `wf-50-error-handler` | Error Trigger | Catches unhandled failure anywhere → dead-letter |
| `wf-51-dlq-reprocess` | Manual | Safe replay. **Edge case 14** |
| `wf-60-ops-summary` | Cron/Manual | The §3.J summary query |

Intake workflows acknowledge immediately and do no processing — the standard queue-in-front-of-work pattern. It is what lets edge case 1 be resolved once, downstream, instead of racing between two webhook handlers.

## 10. Audit trail

The requirement (§3.J) is that any single lead's outcome be reconstructible. The trap is logging *messages* instead of *decisions with their inputs*: "routed to manual review" is unreconstructible; `{decision: manual_review, rule: ai_rules_conflict, score: 34, band: unqualified, ai_label: high_potential, ai_confidence: 0.81, predicate_version: v1}` is.

`event_log` is append-only, one row per decision: `ts, lead_id, workflow, execution_id, step, event_type, decision, inputs, outputs, idempotency_key, severity`. Critically it shares a store with `idempotency_claim`, so "what happened" and "what we promised to do" are joinable in one query. A single lead's full history — every decision, every retry, every external effect and its outcome — is one `WHERE lead_id = ?` across two tables.

## 11. Known limitations (Phase 1 view; extended as built)

1. **Real Odoo has no Stripe-style idempotency keys.** Its XML-RPC/JSON-RPC API offers no `Idempotency-Key` header. The mock implements one, which makes the demo cleaner than production. The honest production design is the client-side claim (§4.2b) plus a reconciliation *search* on an indexed custom field `x_idempotency_key` with a uniqueness constraint. The claim/commit protocol is unchanged; only the reconciliation read is more expensive. **This is the most significant mock-to-production divergence in the submission.**
2. **Postgres-as-queue is volume-bounded.** Correct and simple at hundreds/day; the 1-minute tick becomes the bottleneck long before Postgres does. Above ~10⁵/day this wants a real broker.
3. **1-minute tick granularity** means the 30-minute SLA fires at 30–31 minutes. Acceptable; stated so it is not mistaken for a bug.
4. **Edge case 12 compensation is deliberately partial.** Already-delivered messages cannot be recalled; only future effects are cancelled. No retraction message is sent, because a second unsolicited contact is worse than silence (D-020).
5. **Dedup thresholds are unfitted priors.** No labelled data exists. Mitigated by logging full feature vectors (D-011).
6. **n8n's built-in node retry is unused**, so retry behaviour is not visible on the canvas — it lives in the queue. Worth knowing before a reviewer asks where the retry configuration is.

## 12. n8n mechanics referenced above

One line each, for the mechanisms that would need defending under questioning.

- **Execution model** — one execution per trigger firing. Node-level `retryOnFail` retries *within* an execution at a fixed short interval (seconds, capped); there is no partial resume, so a failure late in a workflow re-runs from the top on manual retry. This is precisely why idempotency must be external.
- **`$getWorkflowStaticData('global')`** — per-workflow KV store, flushed only at execution end, no CAS, racy under concurrency. Unused here for anything correctness-critical (D-001).
- **`Wait` node** — two modes: time-based (short waits sleep in-process; longer ones offload the execution to the database and resume later) and "on webhook call" (execution parks in `waiting` until a resume URL is hit). Neither can be cancelled or signalled from outside, which is what rules it out for follow-ups (D-005) and approvals (D-013).
- **Execute Workflow node** — invokes a sub-workflow, optionally awaiting completion. Used for synchronous fan-out within the pipeline, not across time boundaries.
- **Error Trigger** — a workflow containing this node can be set as another workflow's *Error Workflow* in its settings; it receives execution metadata and the error. This is how `wf-50` catches failures that escape in-flow handling.
- **Expressions** — `{{ $json.field }}` for the current item, `{{ $('Node Name').item.json.x }}` to reach a named upstream node, `{{ $execution.id }}` / `{{ $workflow.id }}` for execution context. Note that `$execution.id` appears in `event_log` for traceability but is *deliberately excluded* from every idempotency key (D-002).
- **Queue mode** — n8n with a Redis-backed worker pool; multiple workers execute concurrently. Assumed throughout, which is why `SKIP LOCKED` and OCC are not optional.

## 13. Decisions that are yours, not mine

1. **Is auto-merge permitted at all?** Some clients mandate that every merge is human-approved. That is risk appetite, not engineering. My recommendation is to keep auto-merge at ≥ 0.90 given merges are non-destructive, but the threshold is one env var away from infinity.
2. **VIP approval timeout — fail-open or fail-closed?** If a manager does not respond within N minutes, does the outreach send anyway, or does the lead sit? Fail-open risks an unapproved message to a strategic account; fail-closed risks silence on your highest-value lead. I lean fail-closed with escalation to a second approver, but this is a business call.
3. **Workflow count (12).** Each is small and the decomposition is principled, but if the reviewing audience prefers fewer, larger canvases, the three intake workflows are the obvious merge candidate.
